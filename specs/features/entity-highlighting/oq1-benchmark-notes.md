# OQ-1 benchmark notes: highlight-rescan latency (Task 7)

Working note. Not part of the committed feature spec (`specs/features/entity-highlighting.md`),
which is final and untouched by this task. This file records the measurement
Task 7 produced; Task 8 selects a mitigation from these numbers (do not add a
mitigation this data doesn't call for).

Harness: `frontend/tests/entityHighlightBenchmark.test.ts`. Run with:

```
pnpm --filter getwrite-frontend exec vitest run entityHighlightBenchmark --reporter=verbose
```

The corpus is generated by a seeded PRNG (mulberry32), so the generated text
and term lists are byte-identical on every run — only the measured wall-clock
timings vary run to run and machine to machine. Measured on the development
machine used for this task (Node/Vitest, single run reported below; a second
run is included to show run-to-run stability).

## Method

- 9 corpora: word counts {500, 2500, 5000} x declared-term counts {50, 200, 500}.
- Declared terms are synthetic name-like strings (e.g. `Kaelbren0`); the
  benchmark treats "declared term count" as the unit that matters, per the
  task brief's "name + a couple aliases each is fine — the important thing is
  total declared term count."
- Each document sprinkles term occurrences (bare, possessive, and simple
  plural forms) at ~4% of word positions so every variant has real matches to
  find, not just filler text.
- **Baseline**: one `findMentionOffsets` call per declared term against the
  full document text, summed — the naive per-term approach.
- **Mitigation (a) combined alternation regex**: builds a single regex
  alternating all declared terms (longest-first, so a longer term is
  preferred over a shorter one that is its prefix) with the same boundary/
  possessive/plural envelope `findMentionOffsets`'s `buildAliasRegex` uses,
  and scans the document once. Simplification: this variant does not
  disambiguate which alternative matched when two terms share a prefix (a
  production implementation still needs a lookup from matched text back to
  the owning term/entity) — it measures scan cost, not classification cost,
  which is the fair, comparable slice of the work each variant shares.
- **Mitigation (b) step-map-scoped rescan**: simulates inserting one word at
  the document's midpoint (the smallest realistic per-keystroke edit) and
  rescans only a window of ±500 characters around the edit, per term, using
  the same `findMentionOffsets` calls as the baseline restricted to that
  window.
- **Mitigation (c) debounce**: not a compute-time measurement — see below.

**500-alias/5000-word ceiling** (the combination the task calls out

**Observation on what drives baseline cost**: across both runs, baseline
elapsed time tracks the *alias count* far more strongly than document length
— e.g. at 500 aliases, elapsed time is ~130-152 ms whether the document is
500 or 5000 words, while at 50 aliases it stays ~13 ms across all three
document lengths. This is consistent with the baseline's cost being
dominated by per-term regex construction (`findMentionOffsets` builds a new
`RegExp` per call, and the baseline makes one call per declared term) rather
than by scanning through more document characters, at the document lengths
this benchmark covers. This is a measurement of what the numbers show, not a
diagnosis of the production code path — Task 8 profiles its own
implementation before deciding anything from it.

## Debounce (mitigation c) — descriptive, not a raw timing

Debouncing does not change the cost of a single rescan; it changes how often
a rescan runs relative to keystrokes. Given the baseline's per-scan cost
above, a debounce window of, for example, 150 ms would coalesce a burst of
rapid keystrokes (a typical fast typist producing a keystroke every ~60-120
ms) into roughly 1-2 rescans instead of one rescan per keystroke — but it
does not lower the cost of the rescan that does eventually run, and it
introduces a visible lag between typing and the highlight updating (up to
the debounce window's length) that other mitigations do not. It is a
complementary policy, not a substitute for the baseline being fast per-scan.

## Threshold

**Recorded threshold: 50 ms** for a full highlight rescan triggered by a
single keystroke.

Justification: this is not an invented number — it is grounded in two
established, converging input-latency guidelines:

- Nielsen's response-time limits: "0.1 second is about the limit for having
  the user feel that the system is reacting instantaneously" (Jakob Nielsen,
  *Usability Engineering*, 1993; restated in the widely-cited 2014
  Nielsen Norman Group article "Response Times: The 3 Important Limits").
- Google's RAIL performance model: "Respond to user input in under 100ms" for
  the interaction to be perceived as instant.

Both guidelines set the *whole* perceived interaction — the browser
processing the keystroke, the highlight rescan, any React re-render, and
paint — at roughly 100 ms. The rescan is one contributor among several in
that budget, not the only one, so this note records 50 ms specifically for
the rescan step alone, leaving headroom in the same 100 ms budget for
transaction dispatch, re-render, and paint on top of it.

## Which mitigation(s) the numbers show are necessary

At the 500-alias/5000-word ceiling, the unmitigated baseline (136.8-137.3 ms)
exceeds the 50 ms threshold by roughly 2.7x — the baseline alone does not
meet FR-9 at this ceiling, so "zero mitigations" is not supported by the
numbers.

Both of the two compute mitigations profiled independently bring the same
ceiling combination comfortably under the threshold on their own:

- Combined alternation regex alone: 1.886-1.938 ms — about 70-75x under the
  50 ms threshold.
- Step-map-scoped rescan alone: 0.523-0.680 ms — about 75-95x under the
  50 ms threshold.

The measurement does not show that *both* are required together, nor that
debouncing is required at all — either the combined-regex approach or the
scoped-rescan approach alone already clears the recorded threshold with wide
margin at the worst-measured combination. Debouncing (mitigation c) is not
shown to be necessary to meet the threshold, since either compute mitigation
alone already does; it remains available as an additional policy layer if a
future measurement (e.g. under real ProseMirror decoration-application cost,
which this benchmark does not include) narrows that margin.
